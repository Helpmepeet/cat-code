# Build and install Cat Code

Use this only for an explicit build or installation request in the Cat Code repository. Updating this skill or asking how installation works does not authorize an installation. Read the current `CLAUDE.md`, `docs/migration/decisions/LOCAL-USE-CONTRACT.md` including its GitHub delivery amendment, `.github/workflows/{ci,delivery}.yml`, `app/scripts/package-app.ts`, and `app/scripts/install-local-app.sh` before acting; source and current repository instructions take precedence over this skill.

## Select the source

Inspect the branch, `HEAD`, working tree, origin repository, and existing `/Applications/Cat Code.app`. Identify which changes the user wants in the app. A shared checkout can contain another session's edits: do not include them accidentally, stash them, or clean them.

For an ordinary install/update request, target committed `HEAD` locally without waiting for CI, even if CI is pending or failed for that commit; report any known failure. Check for an already installed or prepared build before starting tests or packaging. Build only when no reusable exact artifact is available. A request for a verified or GitHub build uses the verified GitHub delivery below. A request to build without installing uses the local-build path and stops before installation. If the user requested particular changes, a build that lacks them is not a substitute: report uncommitted work rather than committing it. For "latest verified build", select the newest eligible delivered version, but disclose newer local or remote changes that it excludes.

On the verified route, if the matching CI or delivery run is pending or failed, or its artifact is missing, expired, or inaccessible, report that condition. Do not silently install an older version, rebuild locally, push changes, or rerun GitHub workflows. Offer waiting, investigating the failure, or a local build; preserve any build route the user already requested.

Building, installing, pushing, and launching are distinct actions. An explicit request to build and install authorizes that run's build and replacement steps; a build-only request does not authorize installation. Push only when separately requested. For a requested push, fetch the current remote, inspect divergence, verify the destination and signed-in account, and use a normal non-force push. Do not publish another session's uncommitted work.

## Reuse before rebuilding

For a local installation request, first use the maintained installer's read-only `skip_current_install` helper in a separate Bash process, with `repo_root` set to the repository root and the selected full SHA. A verified no-op means stop without tests, packaging, replacement, or launch. A nonzero result is not proof of a healthy installed build: inspect the reason and preserve lock/duplicate-app blockers. For an explicitly GitHub-verified request, establish the requested provenance through the GitHub route first; an intact locally installed build is not automatically CI-verified. A build-only request still produces an artifact rather than stopping at an installed-app no-op.

Next inspect known prepared-bundle paths from this task or a previous preparation. Reuse a bundle only when its signature, bundle ID, executable, and sealed source SHA verify, and available successful check records establish the full desktop suite for that clean source before packaging and headless smoke for that unchanged bundle. Matching SHA or a plausible filename alone is insufficient evidence. Do not claim evidence you cannot retrieve or use an older build to satisfy a request for newer changes.

Install an eligible prepared bundle through `install:local --bundle ... --commit FULL_SHA --no-launch`. Do not rebuild it or rerun the full suite just because this is another installation attempt. Preserve the prior check evidence and distinguish it from checks performed now. Reverify the bundle before replacement; repeat smoke if the existing artifact-specific evidence is insufficient. If source validation is missing, a check failed, or the artifact was changed, expired, or removed, report the gap and use the new-build procedure rather than calling it already validated.

## Download and verify the GitHub build

1. Use the authenticated `gh` CLI for the repository identified by origin. Read current workflow definitions rather than trusting a remembered run, URL, or artifact name.
2. Identify the full 40-character source SHA and successful `CI` and `Desktop delivery` runs for that source. Require same-repository `main` delivery from an eligible push/manual CI run, not a pull-request artifact. Confirm the packaged source through the delivery summary, artifact identity, and bundle verification; a `workflow_run` workflow's own head SHA is not by itself proof of the packaged source. Success for a different source SHA is insufficient.
3. Select the unexpired artifact belonging to that successful delivery run. With the current workflow its name is `cat-code-macos-arm64-FULL_SHA`. Download only that artifact to a fresh temporary directory with `gh run download DELIVERY_RUN_ID --repo OWNER/REPO --name ARTIFACT_NAME --dir DOWNLOAD_DIR`. Do not extract into the shared checkout or `/Applications`.
4. The artifact contains an inner app ZIP and its `.sha256` file. Verify the inner archive with its SHA-256 file before extracting it into isolated staging. A mismatch stops installation; do not regenerate the checksum, re-sign, or rebuild to make it pass.
5. Verify the extracted bundle's deep strict code signature, `com.catcode.desktop` identifier, arm64 executable, and full source SHA inside the sealed ASAR. The archive name alone does not prove its contents. Keep the bundle intact, including its compiled sidecar and companion resources.
6. Prepare a clean temporary checkout of the selected SHA with its own frozen root/app dependencies. Place the verified downloaded bundle at that checkout's `app/dist-app/Cat Code.app`, the path the current packaged smoke script reads. Run `bun run --cwd app smoke:packaged:headless` there against the downloaded bundle. Do not run `package` first: that would replace the download with a different artifact.
7. Install that exact verified bundle using the maintained `install:local --bundle ... --commit FULL_SHA --no-launch` path below, from the prepared checkout. Do not use the default installer command for this route: it rebuilds committed `HEAD`.

GitHub's archive retention is finite; check the artifact's actual expiry. This is an ad-hoc-signed personal build, not Developer ID signed or notarized. Signature and smoke checks do not establish Gatekeeper acceptance, GUI behavior, or live-account behavior. Report a first downloaded build's remaining target-Mac checks, and do not remove quarantine, disable Gatekeeper, or bypass a security refusal to force it open.

## Build locally

Prefer a clean committed snapshot of the intended ref in a temporary clone when the checkout has unrelated changes. Install dependencies inside the selected clean checkout with `bun install --frozen-lockfile` at the root and in `app/`; do not link either `node_modules` directory from the shared checkout. The default installer does this automatically for committed `HEAD`. A lockfile mismatch must fail the build rather than update the lockfiles. Confirm the build prints the intended commit without a dirty suffix.

When a new artifact is needed, run `bun run --cwd app test:all` from the selected clean source before packaging, as `CLAUDE.md` requires. Stop if it fails; do not package or install through that failure. Run the suite once for this preparation, not again on a retry that reuses the same validated source and unchanged artifact. Local preparation can take as long as the full suite: not waiting for GitHub CI does not make a new local build a quick install.

After the required checks pass, run `bun run --cwd app package` once from that source. Verify the produced `app/dist-app/Cat Code.app` with `codesign --verify --deep --strict`, its `com.catcode.desktop` bundle ID, executable, and embedded build SHA. Run `bun run --cwd app smoke:packaged:headless`, which checks the bundled sidecar and ripgrep with scratch state. Retain the selected SHA, clean-source/check results, bundle path, and artifact-specific smoke result for reuse, then install with `--bundle` instead of the default command that builds again. Routine installation does not need the GUI smoke or a UI inspection. Use those only when the user requests GUI verification or when diagnosing an observed launch failure. Do not use the user's live profile as a smoke-test substitute.

## Install when requested

Prepare the selected build while Cat Code remains open; do not ask the user to quit before downloading, building, or verifying it. Use the maintained installer below rather than recreating its copy/move commands. It verifies the installed build and skips replacement when the requested commit is already installed and intact, even while the app is running. An integrity failure must take the repair path, not be reported as already installed.

If the installer reports a prepared build but refuses replacement because Cat Code is running, report "prepared, not installed" and retain the printed build/checkout paths and exact retry command. Ask the user to quit only then, and retry that same artifact without rebuilding or changing the selected commit. Temporary files can expire; if the retained artifact is gone, report that preparation must run again. Do not stop a process you did not start, bypass an install lock, or treat a nonzero installer exit as success.

- For a new local build, complete the full-suite, package, and headless-smoke preparation above, then use `--bundle` below. The default `install:local --no-launch` builds committed `HEAD` but does not run `test:all`; it is not a substitute for the required validation.
- Omit `--no-launch` only when the user authorized reopening the app.
- For the downloaded verified bundle, or a bundle already packaged and headless-smoke-tested from the selected clean source, run `bun run --cwd app install:local --bundle "/absolute/path/Cat Code.app" --commit FULL_SHA --no-launch` from the prepared checkout. This avoids rebuilding a different checkout. Omit `--no-launch` only with launch authorization.

An ad-hoc signing warning explains why macOS may ask for file access again after an update; it is not an installation failure. These installer improvements do not preserve privacy approvals across changed builds. Do not re-sign the app, create certificates, reset privacy permissions, or bypass Gatekeeper as part of a routine installation.

The install is complete only when `/Applications/Cat Code.app` is the sole visible production Cat Code app in `/Applications`, its signature and embedded SHA match the selected build, and the final app is registered with Launch Services. Development bundles have a separate identity and are outside this cleanup. The installer stages under `/Applications/.cat-code-install.noindex/` and retains one previous build in `~/Library/Application Support/Cat Code Install Backups.noindex/`; it retires older identified inactive installer backups only after the replacement verifies and registers. Never create visible `.staging-*.app` or `.rollback-*.app` siblings in `/Applications`.

On failure, preserve recovery artifacts and report the actual installed/rollback state. An interrupted-install lock or extra visible production app requires inspection; do not bypass the lock or sweep another session's artifacts. Do not report success while duplicate-app or registration checks fail. Launcher caches can refresh later, so distinguish filesystem/registration checks from an observed launcher UI.

Report the selected route (GitHub download, reused local artifact, new local build, or already-installed no-op), installed path and SHA, CI/delivery run links when used, retained rollback path, and whether the app was launched or observed running. State which checks actually ran now, which successful results were reused and their source/artifact, and any failures, skips, or missing evidence. Never claim the full suite did or did not run without checking the actual record. For local builds, report whether the commit is pushed and its CI result if known; a local pass is not a GitHub CI pass, and a pre-existing failure is not automatically harmless. Leave unrelated working-tree edits untouched.
