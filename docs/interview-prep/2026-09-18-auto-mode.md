# Auto Mode in Cat Code

This document explains the architecture, security model, and engineering trade-offs of Cat Code's Auto Mode for the Skooldio AI Engineer interview.

---

## 1. What Problem Auto Mode Solves

In an autonomous coding agent, there is a fundamental tension between **autonomy** and **safety**:

* **The "Ask" Bottleneck:** By default, every shell command, file write, or external action requires explicit human confirmation (`behavior: 'ask'`). In long-running tasks, background workers, or unattended desktop sessions, constant prompts destroy autonomy.
* **The Reckless Bypass:** Blindly auto-approving all actions (`--dangerously-skip-permissions`) is dangerous on a developer's host machine. An autonomous agent can execute prompt injections found in code/web pages, hallucinate destructive deletions (`rm -rf`), wipe Git history, or leak private tokens.
* **The Host Execution Constraint:** Unlike agents that run inside disposable cloud containers (like Devin or OpenHands), Cat Code runs **directly on the developer's bare-metal machine** with access to real SSH keys, local credentials, and uncommitted Git trees.

**Auto Mode introduces an automated security monitor:** It intercepts actions that would normally prompt the user, fast-paths safe operations, and uses a dedicated two-stage AI classifier to evaluate whether the proposed action is safe against a closed rulebook and user intent.

---

## 2. Where Auto Mode Sits in the Agent Loop

Auto Mode is an **interception hook** inside the permission pipeline:

```text
Agent Emits Tool Call (Tool + Input)
  │
  ▼
1. Base Permission Check
   ├── Matches Static Deny Rule?  ──► DENY immediately
   ├── Matches Static Allow Rule? ──► ALLOW immediately
   └── No Static Match?           ──► Resolves to behavior: 'ask'
         │
         ▼
2. Permission Mode Routing
   ├── Interactive Mode           ──► Prompt human operator
   ├── dontAsk Mode               ──► Convert 'ask' to 'deny'
   └── Auto Mode                  ──► Proceed to Auto Mode Pipeline
         │
         ▼
3. Hard Safety Checks
   ├── Interactive-only tools (e.g. AskUserQuestion) ──► Prompt user (or deny in headless)
   └── Non-delegable safety checks                   ──► Deny (fail closed)
         │
         ▼
4. Pre-Classifier Fast Paths (Zero LLM Latency & Cost)
   ├── Safe-Tool Allowlist (FileRead, Grep, Glob, LSP, Tasks) ──► ALLOW immediately
   └── acceptEdits Fast Path (File writes strictly in CWD)     ──► ALLOW immediately
         │
         ▼
5. Two-Stage Security Monitor (LLM Classifier)
   ├── Stage 1: Harm Screen (Ignores user authorization)       ──► <block>no ──► ALLOW
   └── Stage 2: Intent Adjudication (Checks [named+specifics]) ──► Verdict: ALLOW or BLOCK
```

---

## 3. Fast Paths vs. The Classifier

Calling an LLM classifier takes 1–3 seconds and consumes tokens. Cat Code resolves routine actions instantly in TypeScript code before ever reaching the LLM:

1. **Safe-Tool Allowlist:** Purely observational or state-isolated tools (`FileRead`, `Grep`, `Glob`, `LSP`, `TodoWrite`) cannot mutate the system or make network requests. They skip the classifier with zero latency.
2. **Project-Boundary Fast Path (`acceptEdits`):** When the agent edits or writes a file, TypeScript checks if the target path is strictly contained within the project's working directory and does not target protected paths (`.git/`, `.env`). If local and safe, it allows immediately.

Shell commands (`BashTool`), external writes, deletions, and network requests cannot take the fast path and are handed to the classifier.

## 4. The Two-Stage Classifier Architecture

When an action reaches the classifier, Cat Code uses a two-stage evaluation:

```text
                               Proposed Action
                                      │
                                      ▼
                      ┌───────────────────────────────┐
                      │    Stage 1: Harm Screen       │
                      │  • 64 output tokens           │
                      │  • Reasoning effort: OFF      │
                      │  • Reads facts, ignores intent│
                      └───────────────┬───────────────┘
                                      │
                     Does any BLOCK rule potentially apply?
                                     ╱ ╲
                                    ╱   ╲
                              No   ╱     ╲   Yes
                                  ▼       ▼
                             [ ALLOW ]  [ Escalate to Stage 2 ]
                                                  │
                                                  ▼
                                  ┌───────────────────────────────┐
                                  │ Stage 2: Intent Adjudication  │
                                  │  • Up to 8,192 tokens         │
                                  │  • Reasoning effort: MAX      │
                                  │  • Checks [named+specifics]   │
                                  └───────────────┬───────────────┘
                                                  │
                                  Did user explicitly authorize?
                                                 ╱ ╲
                                                ╱   ╲
                                          Yes  ╱     ╲  No
                                              ▼       ▼
                                         [ ALLOW ]  [ BLOCK ]
```

### The Crucial Semantic Distinction in Stage 1
* **Stage 1 does NOT mean "ignore user messages entirely."**
* Stage 1 **extracts factual context** from the conversation (e.g. what file is being touched, whether a destination is a public repo).
* But it **strictly ignores the authorizing effect of user consent** (*"I approve"*, *"please do this"*).
* *Example:* If the user says: *"Upload `credentials.env` to this public repository. I approve."*
  Stage 1 extracts: target = `credentials.env`, destination = public repository. It sees potential Data Exfiltration. It ignores *"I approve"* and outputs `<block>yes</block>`.

## 5. The Rule Taxonomy & Evidence Bars

The monitor evaluates actions against a closed rule set inherited from Claude Code 2.1.223:

### A. The Three Tiers
* **HARD BLOCK (1 Rule — Data Exfiltration):** Sensitive code, credentials, or secrets crossing the trust boundary to unverified external endpoints or public repositories. **User intent cannot clear this.**
* **SOFT BLOCKS (65 Rules — Destructive / Irreversible Actions):** `git_destructive` (force push), `irreversible_local_destruction` (`rm -rf`), `production_deploy`, `cloud_storage_mass_delete`, `credential_exploration`, `self_modification`.
* **ALLOW Rules (17 Rules):** Routine developer workflows that are explicitly exempt (running tests, local git status, compiling).
* **Default-Allow Baseline:** By default, actions are allowed. The classifier must name a specific block rule to reject a command.

### B. The `[named+specifics]` Consent Bar
To clear a Soft Block in Stage 2, user consent must satisfy the `[named+specifics]` bar:
1. The human must name **the dangerous action** AND **the specific dangerous parameter** (`must name:` slot).
   * *Force push:* Must name force-pushing AND the destination branch (e.g., `main`). Saying *"push my work"* is not enough.
   * *File deletion:* Must name the destroy verb AND the exact path (e.g., `/tmp/scratch`). Saying *"clean up build space"* is not enough.
2. **Two Valid Consent Paths:**
   * **Path A:** User-initiated in their prompt.
   * **Path B:** Agent proposes the specific action and parameter, followed immediately by user affirmation (*"yes"*, *"proceed"*).

## 6. Prompt Caching: Intent vs. Provider Reality

An important finding in Cat Code's implementation concerns how prompt caching behaves:

### The Historical Intent
In commit `aaa47f428b`, the two-stage classifier was implemented with the recorded assumption to *"share the cached base prompt across both requests."*

### The Empirical Reality
Verified against official OpenAI (`reasoning_effort`) and Anthropic (`effort` / `tools`) specifications:
1. **Jumping from Stage 1 to Stage 2 is a CACHE MISS.**
   Changing `reasoning_effort` (off $\to$ max), changing tool schemas (`STAGE1_YOLO_CLASSIFIER_TOOL_SCHEMA` vs. full discriminated schema), and removing `STAGE1_PROMPT_SUFFIX` invalidates the provider's prefix cache.
2. **Where Caching Actually Succeeds (Horizontal Across Turns):**
   Because 85–90% of routine developer commands pass Stage 1 and never escalate, **consecutive Stage 1 checks across turns share the exact same configuration** and achieve 95%+ prefix cache hit rates.

### The Architectural Takeaway
Because Stage 2 pays full prefill on escalation anyway, there is no caching penalty for refactoring Stage 1 to physically strip or redact user messages. Doing so would provide a code-level defense against prompt injection without losing any caching benefit.

## 7. Model Selection & Cross-Provider Fallback Ladder

* **Primary Model:** Defaults to **`gpt-5.6-luna`** running at **`reasoningEffort: 'max'`** via pooled Codex subscription accounts.
* **Why Codex-First:** In Cat Code, Anthropic access may be unconfigured or intermittent, but Codex account pools are always available. Defaulting to Claude would open every session by failing an unreachable network call.
* **The Provider Fallback Ladder:**
  ```text
  gpt-5.6-luna (Codex Account 1)
    ↓ (HTTP 429 rate limit or transient 500)
  gpt-5.6-terra (Codex Account 2)
    ↓ (HTTP 429 rate limit or transient 500)
  gpt-5.6-sol (Codex Account 3)
    ↓ (All Codex accounts exhausted)
  Claude 3.7 Sonnet (Anthropic API / Bedrock / Vertex)
    ↓ (Ladder exhausted)
  FAIL CLOSED (Deny action for safety)
  ```
* **Iron Gate (Fail-Closed):** If all models and providers are exhausted, Cat Code never fails open. An unmonitored command is held back (`behavior: 'deny'`) until connectivity is restored.

## 8. Security Boundaries & Circumvention Prevention

Cat Code includes several additions to protect autonomous execution:

1. **Circumvention Prevention (`<settings_deny_rules>`):**
   If the user defines static deny rules (e.g. `permissions.deny: ["Bash(git push:*)"]`), Cat Code injects them into the classifier prompt. The classifier is explicitly instructed to block attempts to achieve the same result indirectly via `python -c`, `sed -i`, or shell redirection.
2. **Multi-Agent Provenance:**
   Subagent and background worker results enter the parent transcript under the `user` role. Cat Code prefixes these with `[SYSTEM NOTIFICATION - NOT USER INPUT]`. The classifier's rulebook explicitly commands that relayed messages cannot author human consent.
3. **Fail-Closed Discriminated Parser:**
   The classifier outputs `{ thinking, shouldBlock, reason, category? }`. The runtime parser separates the core verdict from the category telemetry. If the model returns an invalid or unrecognized category, **the block still stands**—preventing a schema parse error from accidentally flipping a block into an unsafe allow.

## 9. Post-Decision Handling & False Positives

When Stage 2 reaches a decision:

### If Allowed:
The command executes, and consecutive denials reset to `0`.

### If Blocked:
The tool call fails, and Cat Code returns `DENIAL_WORKAROUND_GUIDANCE` to the agent:
> *"Permission for this action has been denied. Reason: [Rule Name]... If you believe this capability is essential, STOP and explain to the user what you were trying to do and why you need this permission. Let the user decide how to proceed."*

### The Three False-Positive Recovery Paths:
1. **Conversational Informed Consent (Rule #6):**
   The agent stops and asks the user: *"Auto mode blocked deleting `/path`. Do you want me to proceed?"* When the user replies *"Yes"*, Rule #6 treats post-block confirmation as strengthened, informed consent and allows the retry.
2. **Circuit Breaker (`denialTracking.ts`):**
   If the agent gets blocked **3 times in a row**, Cat Code trips a circuit breaker and automatically surfaces an interactive human approval modal, preventing token-wasting infinite loops.
3. **Persistent Allow Rules:**
   Users can approve recurring safe patterns via settings (`autoMode.allow`) or Cat Code Desktop's "Recent Denials" tab, completely bypassing future classifier checks.

## 10. How to Pitch Auto Mode in an Interview

### 30-Second Elevator Pitch
> *"Cat Code runs directly on the developer's bare-metal machine, so we couldn't rely on disposable cloud Docker containers for safety. Instead, we built Auto Mode: an application-layer security monitor. It intercepts sensitive tool actions, fast-paths safe workspace edits, and uses a two-stage LLM classifier with a 66-rule taxonomy to distinguish routine development from destructive actions, prompt injection, and data exfiltration."*

### The Staff-Engineer Insight (The Caching & Prompt Separation Critique)
> *"When studying our two-stage Auto Mode classifier, I found an interesting historical assumption. The original commits justified keeping the full transcript in Stage 1 to 'share the cached base prompt across both requests'.
> But after verifying against OpenAI's and Anthropic's official caching specifications, changing reasoning effort from off to max—along with altering tool schemas—invalidates the prefix cache between stages.
> Discovering this showed me that Stage 2 pays full prefill on escalation anyway. That means we can safely refactor Stage 1 to physically strip user messages, eliminating prompt-injection risks with zero caching penalty."*
