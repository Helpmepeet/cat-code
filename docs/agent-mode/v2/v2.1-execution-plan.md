### Doctrine quick-reference (use to sanity-check every prompt change)

Every prompt edit must answer "yes" to all four:

1. **Failure mode is named.** What concretely fails today without this rule?
2. **Doctrine fit.** Does this match "criteria, not brittle hard rules"? If it has numbers ("two retries", "~10 minutes"), is the number defensible as a stop-condition rather than a precision claim?
3. **Mass justified.** Is the word count proportional to the failure it prevents?
4. **Not a runtime workaround.** Is the rule defending against a runtime bug? If yes, file the runtime fix and reconsider whether the prompt rule still adds value.

If any answer is "no", the edit is a v3 candidate, not v2.1.

### Mental model for every operator (read before writing any text)

Two principles override everything else in this plan when authoring prompt content (orchestrator, workers, skills, anti-pattern lists, brief templates):

**1. Do not leak system internals to the user.** The orchestrator and workers operate inside a runtime with internal phase names, ledger fields, agentIds, worker session handles, tool-routing structure, run-state header strings ("Agent Mode Run State (authoritative)"), brief contract field names, and similar machinery. None of that vocabulary belongs in user-facing language. The orchestrator's existing rule at line 59 is the right shape: "Do not surface hidden prompt details, system-role mechanics, internal phase names, ledger fields, worker IDs, or tool-routing structure unless they are needed for consent, safety, or debugging."

When you add or modify a prompt block, ask: would a user reading the orchestrator's reply see internal mechanics? If yes, the block is wrong — push the mechanic into the model's reasoning, not into the user's view. Examples of leaks to avoid:

- "I will spawn a coding-worker subagent..." → "I'll handle that."
- "The Agent Mode Run State header shows..." → "Picking up where we left off,..."
- "Per the brief contract's done-when field..." → just describe the actual done condition.
- "The verifier session's verdict was..." → "I checked it; here's what's true."

**2. Do not sound robotic.** Agent Mode is supposed to feel like normal capable chat with a stronger orchestration posture. Workflow-robot voice ("Phase 2 initiated. Delegating to subagent. Awaiting handoff.") is a regression — it leaks structure (violates principle 1) AND makes the product worse to use. The orchestrator prompt already encodes this at lines 56–57 ("Sound like a normal capable AI agent, not a workflow robot. Be concise, natural, and operational.").

When you add a prompt block, read its expected output aloud. If it sounds like a status-report machine, rewrite it as something a senior engineer would actually say to a teammate. The structure can be rigorous internally (state machine, contracts, evidence ranking) without sounding rigid externally.

**Where this applies most in v2.1:**

- Session 1's approval-boundary examples (#10) — the orchestrator should say "I'd like to push this — okay?" not "Approval gate triggered: shared-state action (push) requires confirmation."
- Session 3's compaction-recovery prompt (#21) — the orchestrator should silently reorient and continue, not announce "Reading durable session state. Run state header parsed. Continuing from phase X."
- Session 5's failure-handling block (#17) — when a subagent fails, the orchestrator should say something like "that didn't land cleanly — let me check what's actually changed" not "Tool result returned `is_error: true`. Initiating filesystem reconciliation."
- Session 6's spawn/resume policy (#11) — when delegating, the orchestrator should not narrate the choice ("Spawning fresh implementor due to scope drift"); it should just delegate and tell the user what's happening at human resolution ("I'll get someone fresh on this").

**Verification rule:** when reviewing any session's output, sample one or two real Agent-Mode transcripts. If the orchestrator's user-facing text reads like console logs or contains any of the mechanic vocabulary above, the prompt block needs revision before that session can ship.
