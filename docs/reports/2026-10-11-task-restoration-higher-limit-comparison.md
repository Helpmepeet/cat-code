quality improvement from two repetitions of one repair fixture.

Across the two runs in each arm, off used 42 requests and on used 31 (26.2%

prices or dollar charges were applied to subscription usage.

## What changed for this rerun

The user explicitly requested increasing the limit and rerunning rather than
abandoning the comparison over cost. The subscription runner now allows 64
requests and 20 minutes per attempt, 256 requests and 84 minutes per suite,
with an 8-million inclusive-input reservation allowance per attempt and
32 million per suite. The input estimate and reconciliation behavior are
unchanged. Limits remain emergency stops, not targets for usage. The SDK's
4096 output request remains unenforced by the production subscription translator;
actual output is measured from completed provider responses.

The four attempts ran off/on, then on/off, with the same prepared inputs,
production repair, hidden grader, low effort, manual compaction, fresh-process
resume, subscription HTTP transport and fixed recovery turn as the corrected
earlier pilot. Only the evaluator's request/input/time allowances and recorded
authorization changed. No production code or feature default changed. Each
attempt has a fresh provider identity and independently generated natural
summary, so model/summary variability and server cache effects remain.

No attempt reached any new admission limit. Three attempts used more than the
old 12-request allowance. All four completed an actual successful `bun check.ts`
before recovery and then finished the fixed recovery turn. Artifact grading
ran after the full protocol; pre-recovery check success alone is not a complete
pre-recovery artifact grade.

## Delivery and mistakes

On arms persisted and delivered one restoration block each; off arms delivered
zero. Original tracking exchanges were absent from all first work requests.
No request contained duplicate restoration blocks. Restored task IDs were
1, 2 and 3, excluding completed cleanup, unrelated unowned and foreign-owned
controls.

All eight hidden function checks, README requirements, protected-file checks
and actual verification-call checks passed in all four attempts. The task-state
audit found no changes to unrelated task 5 or foreign-owned task 6. Every arm
deleted already-completed cleanup task 4's metadata; no arm deleted or modified
`archive/ledger.csv`. That task cleanup is disclosed separately from artifact
success and was not counted as revival of its completed file-deletion request.

In the first pair, off made two TaskList and four TaskGet calls while on made
none; in the second pair both arms made those calls. This is consistent with
the reminder sometimes reducing rediscovery, but the behavior did not reproduce
uniformly. All model responses were live and unscripted.
