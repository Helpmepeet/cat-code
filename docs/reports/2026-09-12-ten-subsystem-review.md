## 1. Usage Analytics

**UA1, High: recent work in an old session disappears from the selected window.** [The aggregator](/Users/pt/cat-code/src/utils/stats.ts:194) filters the whole transcript by its first timestamp and attributes its later token credits to that date. A session started eight days ago and continued today with 1,650 fresh-input-plus-output tokens contributes zero to the seven-day view. A yesterday/today fixture attributes all 1,770 tokens to yesterday instead of 120 yesterday and 1,650 today. The public range probe reproduces both ordinary and large-file paths. The fast skip has the same start-date assumption at [stats.ts](/Users/pt/cat-code/src/utils/stats.ts:380).

The usage aggregation owner should attribute measured activity by event date and count sessions active in the selected window/day. A file may be skipped only if it has no eligible recent activity. Cover old-session resumption and cross-midnight activity through the public range entry point.

**UA2, High: split Codex responses lose their final input and cache counts.** [Repeated-message handling](/Users/pt/cat-code/src/utils/stats.ts:272) credits input and cache only on the first record for an API message ID. The normal Codex adapter seeds usage with zero at [message start](/Users/pt/cat-code/src/services/api/codex-fetch-adapter.ts:1802) and supplies real counts [later](/Users/pt/cat-code/src/services/api/codex-fetch-adapter.ts:3176). The shared consumer can persist an earlier content block with zero usage and only put final usage on the last block. The public aggregation fixture with zero first, then 1,200 fresh input, 5,000 cache read, and 450 output reports fresh input 0, cache read 0, and total 450. The current metric should report total 1,650; it intentionally excludes cache read from that total.

The aggregation/provider integration owner should track credited amounts for every usage dimension, preserving deduplication while accepting later increases. Keep the existing nonzero-first regression and add zero-first/final-later cases. The provider-to-persisted shape was verified in source; the fixture does not claim a live provider round trip.

**UA3, Medium: a failed project read replaces good data with zeros.** [The project-directory catch](/Users/pt/cat-code/src/utils/stats.ts:480) converts a failed read into an empty list, so the sidecar never sees the aggregation failure it must handle. A real temporary transcript first produces 120 tokens through the public stats domain; injecting `EACCES` at that project's filesystem read then produces a non-null zero snapshot. This defeats the domain's keep-last-good behavior. The aggregation owner should distinguish absent optional paths from failed reads and preserve the failed/incomplete status through the domain. Test the nested read failure, rather than only replacing the entire aggregator with a throwing stub.

**UA4, Low: model colors disagree between cards.** [Daily-series selection](/Users/pt/cat-code/app/renderer/src/statsState.ts:248) sorts before assigning fallback colors; [the model breakdown](/Users/pt/cat-code/app/renderer/src/statsState.ts:517) assigns before sorting. A two-model fixture gives Luna amber in the chart and blue in the breakdown. Labels remain correct. The renderer owner should use one stable model-to-color mapping across cards and ranges.

Evidence: 127 existing focused tests passed. The parent independently reproduced all six diagnostic scenarios, then reran them after concurrent commit `d58b9f10` changed aggregation to one pass. Every finding persisted against the updated implementation; the source anchors above use that revision. Local evidence: [usage probe output](/Users/pt/cat-code/tmp/subsystem-review-2026-09-12/01-usage-analytics-current-parent.log).

Useful additions after the defects: show measurement freshness, state exactly what the token total measures, and expose main/subagent usage separately when the recorded data supports it. Do not invent account attribution from transcripts that lack it.

## 2. Resumed subagent lifecycle

**RS1, High: a successfully delivered follow-up is forgotten on the next resume.** [Sidechain persistence](/Users/pt/cat-code/src/tools/AgentTool/runAgent.ts:1183) excludes `local-agent-message` attachments. The real query delivers and settles the instruction, then [local-task cleanup](/Users/pt/cat-code/src/tasks/LocalAgentTask/LocalAgentTask.tsx:580) removes its memory record. A public `ResumeAgent` → `SendMessage` → completion → second `ResumeAgent` fixture proves that the first resumed run received the instruction, but the saved transcript and second resumed context both lack it. This exclusion was introduced in committed `201f97b6` and is independent of the current dirty cwd/dedup changes.

The worker lifecycle/persistence owner should persist the exact instruction at a truthful delivery boundary. Merely prepared attachments must not be falsely recorded as delivered. Add a public two-resume regression, including an uncertain or undelivered companion case.

**RS2, Medium: a sibling message is presented as a coordinator instruction.** Public `SendMessage` retains the actual worker's `originAgentId`, but [attachment construction](/Users/pt/cat-code/src/utils/attachments.ts:1119) unconditionally assigns coordinator origin. [Model-facing normalization](/Users/pt/cat-code/src/utils/messages.ts:5789) then tells the recipient that the coordinator sent it and it must be addressed before completion. The probe uses a real foreground worker, whose resolved tool pool actually includes `SendMessage`; it does not assume an unavailable async-worker tool. This is a provenance and instruction-priority defect, with no demonstrated tool-permission bypass.

The messaging/prompt owner should carry authenticated runtime sender identity through normalization and preserve different parent and sibling framing. A stored identity assertion alone cannot protect the final model-facing message.

**RS3, Medium: a worker's failure report has no ordinary consumer.** If A sends B an instruction and B stops before consuming it, [outcome handling](/Users/pt/cat-code/src/tasks/LocalAgentTask/LocalAgentTask.tsx:762) enqueues a report addressed to A without priority. [The queue defaults it to `later`](/Users/pt/cat-code/src/utils/messageQueueManager.ts:235), while [ordinary worker tool rounds](/Users/pt/cat-code/src/query.ts:2129) drain `next`. Main idle consumers correctly exclude worker-addressed items. The public messaging/failure/query probe executes two model rounds and leaves the report queued without showing it to A. A fixture-only `next` priority control delivers it and clears the queue.

The messaging owner should provide reachable delivery at tool rounds, no-tool completion, and the first resumed request. Priority alone fixes only the demonstrated tool-round case. Resume delivery of this distinct report type was source-traced, not separately executed. Ordinary parent completion notifications should retain their intended priority.

Resume otherwise creates a fresh execution under the old worker ID, restores transcript/cwd, and reconstructs current role, tools, model, effort, and permission settings. It does not promise a byte-for-byte restoration of the original spawn environment. Final output returns through task notifications. `SendMessage` addresses other workers; escalation to the parent uses the supported blocked-handoff mechanism.

Evidence: 103 existing tests passed in one focused group; another had 73 pass and one invalid cleanup oracle. Three desired-behavior probes fail as expected against the current bugs; the priority control passes. ## 4. Account switching and failover

**AC1, High: a late cap response aborts after the lease already moved to a healthy account.** A request leaves on A; an allowed mid-turn manual switch moves its owner to B; A's delayed 429 arrives. [Retry handling](/Users/pt/cat-code/src/services/api/withRetry.ts:629) asks to fail over A using the now-B lease. [The manager](/Users/pt/cat-code/src/services/api/codexAccountLeaseManager.ts:430) correctly refuses the identity mismatch, but the caller turns that refusal into terminal account recovery. The real retry/pool/lease fixture makes only one attempt despite both accounts remaining healthy. The 401 path already accounts for an intervening lease move; the 429 path does not.

**AC2, High: one owner's cap prevents another owner from using the only healthy replacement.** Main and a worker send A requests. Main's 429 arrives first, caps A, and moves main to B. The worker's late 429 then sees [a `canFailover()` guard requiring two selectable accounts](/Users/pt/cat-code/src/services/api/codexAccountPool.ts:309). With only B healthy, [the retry path](/Users/pt/cat-code/src/services/api/withRetry.ts:625) skips worker failover and reports all accounts unavailable. The probe leaves main on healthy B and the failed worker on capped A after one attempt.

Both are committed engine defects. The account-retry owner should reconcile the failed request identity with the current lease and look for eligible alternatives relative to that failed identity. Preserve the mismatch protection and true single-account exhaustion behavior. Regressions should prove a second request reaches B for both delayed-response orderings.

**AC3, Medium, observed in uncommitted work: retained failover identity masks a later idle switch.** The current [lease selector](/Users/pt/cat-code/app/renderer/src/leaseState.ts:204) retains B after main failover and lease release, then lets B outrank a later successful own-session switch/snapshot naming C. An idle switch has no holding lease to clear that retained state. The reducer/selector fixture delivers the real result-before-snapshot sequence and observes `sessionAccount=C`, `displayedAccount=B`. The next turn eventually repairs the label.

This observation belongs to the active CC-90 follow-up author; it is not described as a shipped feature. Later authoritative local selection must supersede retained failover identity without letting stale or other-session snapshots undo the release fix.

## 6. Queued messages and interruption

**QU1, High: Send now can consume a message without submitting it to the model.** [The query](/Users/pt/cat-code/src/query.ts:2129) snapshots the pending queue, then awaits attachment preparation. During that wait, [Send now](/Users/pt/cat-code/app/sidecar/sidecarServer.ts:2559) still sees the queue head, aborts the current turn, and reports success. Preparation resumes without cancellation/ownership reconciliation, then [announces and removes the command](/Users/pt/cat-code/src/query.ts:2207). The next model-adapter entry has an already-aborted signal, while the finalizer finds no queued command to start a replacement turn.

The paired probe uses the real sidecar server, controller, both app-session adapters, QueryEngine, query loop, queue, and attachment/lifecycle machinery. With no force, two non-aborted provider requests are submitted and the second includes the queued instruction. With force during the preparation await, only the initial request is submitted; the queue is empty, a transcript attachment remains, and the result is `interrupted / interrupt`. Thus the proven defect is missed execution and false delivery state, not disappearance of the stored text. Model/compaction I/O and the timing barrier are fixture seams.

The queue/interruption owner should make preparation, cancellation, and submission share explicit command ownership. A pre-submission force must leave or return the instruction to a deliverable queue and obtain one non-aborted request, without duplicating UUIDs or transcript rows. Permanent coverage should include text and image-bearing input; this race probe exercises text.

**QU2, Low: multiple refused submissions return to the composer in reverse order.** App applies [the restore helper](/Users/pt/cat-code/app/renderer/src/composerState.ts:1022) separately to each refused submit. Its prepend behavior turns `FIRST`, `SECOND`, and `CURRENT DRAFT` into `SECOND\nFIRST\nCURRENT DRAFT`. The real retained-submit and answer reducers plus the source-verified App loop reproduce it. Content remains editable and recoverable. The composer owner should preserve original submission order across batches and out-of-order replies, keeping the live draft afterward; reversing a single batch is insufficient.

## 8. Conversation history and branching
