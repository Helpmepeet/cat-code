## Deviation (§0 — OPEN DRIFT, operator ruling requested)

`🔁 adapted(600000ms-foreground-ceiling + ABSOLUTE one-foreground-invocation
rule → dwell 45s, 1 re-enum cycle instead of the requested ≥2–3)`.

The task asked for `--dwell-ms 120000` (≥2–3 catalog re-enumeration cycles) in a
single foreground invocation, no background / no wait-loop. These cannot all
hold: the matrix wall time is **≈ 120 + 9 × dwell seconds** (measured: ~10 s
non-dwell overhead per attached run, ~12 s per boot run). The harness caps a
foreground Bash call at **600000 ms (10 min)**:

- dwell=45 s → ~525 s ≈ 8.7 min → **fits** → observes on-attach enum + **1**
  30 s re-enumeration + a plateau-stable resample.
- dwell=60 s (2 full 30 s cycles) → ~678 s ≈ **11.3 min → exceeds the ceiling**.

So `reps=3 × ≥2 full re-enum cycles` is **structurally impossible in one
sub-10-min foreground call** — the same ceiling the load-biased run documented
(it used dwell=40 s for the same reason). I honored the ABSOLUTE
one-invocation/no-background rule (it outranks the illustrative "e.g." dwell) and
capped dwell at the largest value that fits with margin.

**Why the science still holds:** the plateau is flat within the observed window
across **three independent runs** — `attached-cycle-1 ≈ attached-cycle-2` in all
9 attached runs here, `cycle-1 ≈ cycle-2` in the pre-run smoke, and
`cycle-2 ≈ cycle-3` in the prior 40 s run. The plateau is reached by the first
re-enumeration and does not climb further.

**Operator ruling requested (does not self-waive):** to positively observe ≥2–3
*full* re-enumeration cycles you must relax one constraint — either (a) authorize
`run_in_background` for one `ram-measure --dwell-ms 120000` (the ~20-min matrix
runs to completion detached; each probe still self-kills via the F2 `finally` +
signal handlers), or (b) authorize 3 **strictly sequential** foreground
`--reps 1 --dwell-ms 120000` calls (~7 min each, no overlap → no orphan, but no
cross-rep counterbalancing and 3 invocations). I did neither, per the ABSOLUTE
rule.
