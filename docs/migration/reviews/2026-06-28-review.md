# Verdict

**Salvageable, but not executable as written.** The walking-skeleton and vertical-slice strategy are sound. The load-bearing architecture is not: the plan simultaneously requires one Bun engine process per session and claims Electron’s single Node main process can host those engines in-process. Current source contradicts that claim. Stop before P0-1, settle the runtime/process topology experimentally, then rewrite the stale backlog.

## Top 5 things that would sink this

1. **The engine topology is internally impossible as stated.**
   The plan requires N engine processes (`PROGRAM-PLAN.md:33`) but places the engine in Electron’s single Node main process (`PROGRAM-PLAN.md:47`). The engine declares Bun (`~/cat-code/package.json:6`), builds `--target bun` (`~/cat-code/scripts/build.ts:158`), and `QueryEngine` imports `bun:bundle` (`~/cat-code/src/QueryEngine.ts:1`). A Node 24 import probe fails with `ERR_UNSUPPORTED_ESM_URL_SCHEME`.
   **Confidence:** Certain for current source.
   **Cheapest test:** Build a packaged Electron spike using the real QueryEngine. Compare Electron-main, Bun sidecar, and one-Bun-process-per-session.

2. **Single-process multi-session conflicts with global engine state.**
   The engine has one process-global session ID/CWD (`~/cat-code/src/bootstrap/state.ts:434`, `:533`); every submit mutates that global CWD (`~/cat-code/src/QueryEngine.ts:215`). Concurrent controllers in one process are unsafe without a substantial engine refactor.
   **Confidence:** High.
   **Cheapest test:** Run two simultaneous controllers with different CWDs, tools and permission requests; assert zero cross-session leakage and crash one.

3. **Cold agents will implement the superseded architecture.**
   The authoritative plan says fresh Electron build and settled transport, while the backlog says reuse `web/`, choose transport, fix the WebSocket path, and consider Tauri (`backlog/phase0-1.md:22`, `:33`, `:93`).
   **Confidence:** Certain.
   **Cheapest test:** Delete and regenerate P0-1 from the dated decision; reject any remaining `web/`, Tauri, or “choose transport” instructions.

4. **The second existential risk is postponed until Phase 3.**
   The plan names both seam and N-session hosting as project killers (`PROGRAM-PLAN.md:78`), but builds transcript and Permissions before proving two sessions (`PROGRAM-PLAN.md:188`).
   **Confidence:** High.
   **Cheapest test:** Move the headless two-session lifecycle/isolation test into Phase 0.

5. **Security, secrets and persistence are treated as late hardening.**
   This renderer displays untrusted model/tool/Markdown content beside an engine that executes commands and accesses the filesystem. Yet there is no Phase-0 threat model, IPC allowlist, credential lifecycle, state-versioning, crash recovery or CLI/desktop coexistence contract. Electron explicitly requires sandboxing, context isolation, restrictive IPC and navigation policies in its security checklist (https://www.electronjs.org/docs/latest/tutorial/security).
   **Confidence:** High.
   **Cheapest test:** Adversarial renderer test plus CLI/Desktop N/Desktop N−1 compatibility and crash matrix before feature work.

## Findings by lens

### 1. Hallucination / unfounded confidence

- **“Electron can host the Node/Bun engine in-process” is refuted for current source.** Electron main is Node; the engine is Bun-targeted. **Test:** packaged real-engine import, not a mocked controller test.
- **“~5 real message types” is materially false.** `SDKMessage` has **19 union members / 15 top-level discriminants** at `~/cat-code/src/entrypoints/sdk/coreTypes.generated.ts:760`. The runtime schema enumerates 25 variants. **Test:** require an exhaustive adapter fixture.
- **“Rich SDK types” is only partly true.** Data survives the controller seam, but assistant content and stream events are typed `unknown[]`/`unknown` at `~/cat-code/src/entrypoints/sdk/coreTypes.generated.ts:90`. **Test:** compile an adapter reading block discriminants without casts.
- **The inventory says six faked surfaces, but mechanically marks twelve `yes` rows** across `INVENTORY.md:29`–`:95`. **Test:** assign every `yes/partial` row a behavior-spec ID.
- **“~50 sessions ±10” is plausible, not derived.** There are 44 non-cut inventory rows, many bundling 5–11 components. **Test:** explicit row→session min/likely/max mapping.

### 2. Wrong hole / wrong problem

- A fresh production UI is reasonable; shipping the browser-Babel prototype is not. But “every line is a rewrite” overstates the case: keyboard logic, state machines and fixtures can become characterization tests.
- Desktop is not implied by local filesystem access. The existing Bun runtime already exposes a loopback WebSocket service at `~/cat-code/src/web/startRuntimeBackedWebMode.ts:35`. Electron may still be right, but a Bun sidecar provides runtime fidelity and crash isolation.
- `concurrentSessions.ts` is not an app registry. It writes ephemeral PID files and sweeps dead processes (`~/cat-code/src/utils/concurrentSessions.ts:48`, `:163`); it cannot restore tabs or provide general attach/multiplex semantics.

### 3. Bias and blind spots

- The plan flatters “production-grade from the start” while deferring performance, accessibility, error handling, telemetry and the full test suite to Phase 5 (`PROGRAM-PLAN.md:213`).
- File-level anchor counts are not surface coverage. The five zero-anchor files are real, but shared shapes in `data.js` ground parts of Sidebar, slash commands and Orchestrator.
- Missing: secret storage/redaction, IPC authority, state migration/versioning, atomic writes, crash recovery, rollback, same-session CLI/Desktop coexistence, OS support, update channels and measurable N-session budgets.

### 4. Decomposition and dependency logic

- Phase 1’s seam is useful, but it does not retire the declared multi-session risk.
- The dependency map says W4 requires W2 shell + W3 spine (`PROGRAM-PLAN.md:152`); Phase 2 builds Permissions before W2 in Phase 3.
- “Seam walks,” “two sessions live,” “~80% wireable,” and “shippable” are demonstrations, not falsifiable gates. Add packaged-build, event-loss, crash, memory, latency, soak and accessibility thresholds.

### 5. Adapter / boundary thesis

The controller boundary is real and useful: raw `SDKMessage`, subscription, abort and permission promises are verified at `~/cat-code/src/app-runtime/AppSessionController.ts:24`.

The proposed universal adapter is not. Transcript projection, session control and Accounts/Settings/Agents services are unrelated boundaries. “Every later domain plugs into it” (`PROGRAM-PLAN.md:250`) creates a god object.

Split it into:
- Versioned engine/session protocol.
- Stateful transcript projector, including tool-use/result correlation.
- Per-domain services/selectors.

### 6. Internal contradictions and staleness

- Fresh build, not `web/`: `PROGRAM-PLAN.md:30` versus `backlog/phase0-1.md:22`.
- Transport settled: `PROGRAM-PLAN.md:41` versus “decide” at `backlog/phase0-1.md:33` and `INVENTORY.md:33`.
- Electron selected, yet backlog still discusses Tauri at `backlog/phase0-1.md:93`.
- In-process path nevertheless depends on fixing the WebSocket mapper. That is false: raw messages already exist at `~/cat-code/src/app-runtime/sessionEvents.ts:20`; the lossy mapper is only introduced by `~/cat-code/src/web/AppSessionWebSocketServer.ts:69`.
- Phase 1 calls the seam the deepest risk retired; Phase 3 calls multi-session the deepest architectural risk.

## What I would do differently

1. Replace P0-1 with a **packaged topology bake-off**: Electron+Bun sidecar versus a deliberately Node-compatible extracted engine boundary.
2. Require **two concurrent sessions**, distinct CWDs, simultaneous tools/permissions, one forced crash, restart and resume before any transcript fidelity work.
3. Define the versioned IPC protocol, renderer threat model, credential handling and persistence ownership in Phase 0.
4. Keep anchors as source-recon hints, but pin them to an engine commit and add behavioral/visual/keyboard acceptance tests.
5. Regenerate all three documents after the topology decision. The current backlog is unsafe to execute.
