# P5-1 review — package assembly and packaged launch (`35dbd8ec`)

**Date:** 2026-08-19 · **Branch:** `migration` · **Subject:** commit `35dbd8ec`
**Method:** two independent reviewers, deliberately decorrelated — one on correctness
and security, one on spec conformance and honesty of claims. Neither saw the other's
findings. Both rebuilt the artifact themselves rather than reading the author's numbers.

**Verdict: YELLOW from both — accept with named follow-ups.** No Critical defect. The
load-bearing mechanisms (development-path argument preservation, lazy mode dispatch,
codesign ordering, preload and CSP posture) were verified correct from source and from a
real build.

Fixes for everything marked FIXED below landed in the follow-up commit; the STATUS row
records the resulting battery.

## The finding both reviewers reached independently

The first cut's automated proof could not detect the regression it was written to
detect. `packaged-launch-smoke.ts` hardcoded the sidecar path as a literal, so part A
spawned that literal and never `resolveSidecarLaunch`; part B launched the app but never
created a session, and `spawn` of `sidecarCommand` happens only inside
`supervisor.ts:330` `spawnSession()`, which `createSupervisor()` never calls. No
assertion in the file depended on `sidecarLaunch().command` or `.identityMarker` being
correct. A resolver returning the development path under `packaged: true` would have
reported 13/13 on an app that cannot start a session.

The author's prevention test did not catch this, because removing the sidecar binary
fails part A — which used its own literal path.

**FIXED.** Every path in the smoke now resolves through `resolveSidecarLaunch`, and the
app-spawned half is asserted from main's own operational log: a `process.exited` record
with `expected: true` proves the packaged app resolved the in-bundle binary, spawned it,
and it ran to a clean exit. A `process.started` record alone is not sufficient and is not
used — main writes it when it asks to spawn, and an ENOENT for a wrong path arrives
asynchronously afterwards. Re-proven by prevention: hiding the compiled sidecar fails the
two sidecar assertions while the three renderer assertions still pass.

A missed prior art is worth recording: `main.ts` already had `CATCODE_SMOKE_EXIT_MS`,
whose comment states it exists to "prove the sidecar spawns … without needing a visible
window". The author wrote a new smoke without looking for it (CLAUDE.md §8 rule 10).

## Checked and clean

Stated plainly rather than padded, because both reviewers went looking and found nothing:

- **Development-path preservation is exact, arg-for-arg, all five modes**, reconstructed
  from `35dbd8ec^` and run against `resolveSidecarLaunch`. No drift.
- **Marker selectivity holds** in both topologies, including `accounts-pool --bare
  --usage-stats`. The truncation hypothesis was killed empirically: `ps -o command=` via
  `execFileSync` returned a 250-character command line intact.
- **The rename is narrow.** `sessions-catalog` survives untouched as the HostEvent type,
  the preload channel, the diagnostics label, and the cache filename. Only the spawn
  token changed.
- **Lazy dispatch survives bundling.** In the emitted bundle,
  `init_sessionsCatalogWorker2` runs its two engine-free dependencies, then sets
  `CLAUDE_CODE_SIMPLE`, then calls `main3()`, with zero column-0 `init_` calls — nothing
  in the engine graph evaluates eagerly. `argv.splice(2, 1)` yields development-identical
  positions, and `isBareMode` is position-independent.
- **No new privileged path.** Payload is 11 files, no source maps, no development
  preload. `webPreferences` hardening is unconditional, the packaged CSP is the stricter
  branch, and the `file://` load is covered by the `<meta>` CSP in the built index.
- **Codesign is correct.** Nested sidecar signed before the bundle per LOCAL-USE-CONTRACT
  §5; `--verify` reports valid on disk and satisfying its designated requirement. The
  `--deep` concern was checked specifically and stripped nothing: stock Electron helpers
  carry no entitlements.
- **No artifact manifest was smuggled in.** The scan is a pure denylist; the build cannot
  fail from an absent file.
- **No dependency was added**, verified against `app/package.json`, the root package, and
  the lockfiles. Two added lines, both scripts.
- **No em-dash violation** in any user-visible string.

## Not verified

Neither reviewer ran the packaged launch (`smoke:packaged` part B). Launching the `.app`
is a GUI action on the operator's machine and neither had authorization for that run, so
the three renderer-plane assertions rest on the author's evidence. The full live
acceptance — two sessions, a tool run, a permission round-trip, a session switch,
close/reopen — remains operator-owned and open.

## Handoffs to the remaining Phase-5 sessions

- **P5-5c is genuinely unblocked.** One thing it inherits: in a packaged run
  `initializeRuntime` executes inside a `--compile`d binary rather than under `bun run`,
  so its engine-migration-ownership investigation must be done against the compiled
  sidecar.
- **P5-7 job 1 is materially short.** Its subject is CSP, navigation, window-open policy,
  and preload exports *under the packaged renderer*, and the only tool for that is
  `run-hardening-smoke.ts`, which works by `--require` against the source tree. P5-1
  established that Electron ignores `--require` in a packaged app and delivered no
  substitute, so there is currently no way to evaluate anything inside the packaged
  renderer. This is the one thing P5-1 arguably should have delivered and did not.
  Inventing an inspection channel is an inbound-surface question needing a decision, so
  it should be scoped in the dispatch prompt rather than left to the worker.
- **P5-7 job 2 has a related hole.** `memory:trajectory` reads the debug-state export,
  and the packaged path deliberately never writes it — the hardening suite asserts
  exactly that. That must be solved before a packaged leak baseline is possible.
- **P5-7 job 3** is unaffected and fully unblocked.
