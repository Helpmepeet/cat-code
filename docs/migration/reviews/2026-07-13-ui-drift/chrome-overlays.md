## Findings (High → Low)

[High] Banner/Toast "info" tone renders PINK instead of the prototype's distinct BLUE: `tone.ts:14-16`'s own comment claims "the prototype has no distinct hue for info — it reuses accent" and wires `info` → `--tone-info` which is `var(--accent)` (`theme.css:28`, #f472b6). But the prototype's own `Banner` tones table defines `info: { color:'#bfdbfe', accent:'#60a5fa', ... }` (Surfaces.jsx:791) and `ToastHost`'s tones table defines `info: { dot:'#60a5fa', border:'rgba(96,165,250,0.3)' }` (Surfaces.jsx:854) — a distinct blue in both places. Every `<BannerStack>`/`<ToastHost>` call with `tone="info"` (`BannerStack.tsx:79-84,119`; `ToastHost.tsx:163-169,187`) therefore renders the wrong hue family. Fix: redefine `--tone-info` in `theme.css:28` to a blue (e.g. `#60a5fa`, which already exists in-theme as `--color-source-project`, `theme.css:67`) instead of aliasing `var(--accent)`, and correct the misleading comment in `tone.ts:14-16`.

[Med] `Chip.tsx` `tone="accent"` is over-saturated vs the prototype's Chip-specific accent color: the prototype's `Chip` component defines its OWN accent tone as `{ color:'#f9a8d4', ... }` (Surfaces.jsx:43) — the light "pink-300" shade — not the full-strength `#f472b6` brand accent. Our shared `tone.ts:53-61` `accent` entry (`text-accent`/`border-accent/*`/`bg-accent`) resolves to `--color-accent` (#f472b6, `theme.css:8`), which `Chip.tsx:44,49-50` (text/border) and the badge (`Chip.tsx:58-64` via `t.badge`) all inherit. `--color-accent-soft` (#f9a8d4, `theme.css:13`) already exists in-theme and is the EXACT hex the prototype's Chip wants — it's just wired to Sidebar active-nav today, not Chip. Live-visible: `SessionsPage.tsx:364` (`<Chip tone="accent" label="orchestrating" />`) renders in the wrong, more-saturated pink. Fix: give `Chip.tsx` its own accent styling on `--color-accent-soft` (e.g. `text-accent-soft border-accent-soft/* bg-accent-soft/*`) rather than reusing the shared full-strength `accent` tone that Banner/Toast correctly use at full strength (Surfaces.jsx:792 `accent:'#f472b6'` matches ours there).

[Med] `BannerStack` title text and non-primary action-button text use the same saturated shade as the icon, losing the prototype's icon/title distinction: prototype's `Banner` colors the icon with `t.accent` (saturated: e.g. danger `#f87171`) but the TITLE with `t.color` (a distinctly lighter tint: e.g. danger `#fca5a5`, warn `#fde68a`, info `#bfdbfe`, accent `#fbcfe8` — Surfaces.jsx:789-793,805) and non-primary action buttons also use `t.color` (Surfaces.jsx:814). Our `BannerRow` uses the single `t.text` class for BOTH the icon (`BannerStack.tsx:126`) AND the title (`BannerStack.tsx:134`) AND the non-primary action button (`BannerStack.tsx:144-149`) — so title/button text is as saturated as the icon instead of a lighter tint. Fix: add a lighter "soft text" class per tone (`tone.ts` `ToneClasses`, e.g. `softText: 'text-tone-danger/70'` or a dedicated lighter utility) and use it for `BannerRow`'s title + non-primary button text, reserving `t.text` for the icon only.

[Med] `DiagnosticsSection`'s "No issues found" success row has no container, unlike the prototype's tinted "OK" pill: our `WarningList` empty-state renders bare icon+text with no background/border/padding (`DiagnosticsSection.tsx:24-29`, `flex items-center gap-1.5 text-[12px] text-tone-success`). The prototype's closest positive-state indicator ("Up to date") is a tinted pill: `padding:'6px 10px', borderRadius:7, background:'rgba(74,222,128,0.06)', border:'1px solid rgba(74,222,128,0.15)'` (Pages.jsx:865-868). Fix: wrap the "No issues found" row in the same pill treatment used for the warning rows (`DiagnosticsSection.tsx:34-41` already does `rounded-lg border ... bg-tone-warn/5 px-2.5 py-1.5` for warnings) — e.g. `rounded-lg border border-tone-success/15 bg-tone-success/5 px-2.5 py-1.5`.

[Low] Banner background tint is a flat `/10` (10%) for every tone (`BannerStack.tsx:123` via `tone.ts` `softBg`) vs the prototype's per-tone 6-7% (`rgba(...,0.07)` danger, `0.06` warn/info/accent — Surfaces.jsx:789-792); banners read slightly more saturated than the prototype across the board. Fix: lower `softBg` opacity (or give `BannerRow` its own bg override) to `/6`–`/7` per tone.

[Low] Banner/Toast `softBorder` for warn/accent is `/25` (`tone.ts:66-78`) vs the prototype's `22%` (Surfaces.jsx:790,792,853); danger's `/25` already matches the prototype's `0.25` exactly (Surfaces.jsx:789). Fix: change warn/accent `softBorder` to `/22`.

[Low] `Chip.tsx` gap is `gap-1.5` (6px, `Chip.tsx:46`) vs the prototype's `gap:5` (Surfaces.jsx:54). Fix: `gap-[5px]`.

[Low] `Chip.tsx`'s `value` slot always renders `text-text-primary` (#f4f4f5, `Chip.tsx:56`) regardless of tone, vs the prototype's per-tone brighter `valueColor` (`Surfaces.jsx:42-47`: default `#e4e4e7`, accent `#fce7f3`, warn `#fde68a`, danger `#fecaca`, good `#bbf7d0`). Currently dormant — no live caller passes `value` (checked `SessionsPage.tsx`/`RemoteSettingsPage.tsx`, both label-only) — but the primitive itself is wrong. Fix: add a per-tone `valueText` field to `ToneClasses` and use it instead of the hardcoded class.

[Low] `ConnectionChip` padding/gap run a couple px larger than spec and the resting background never dims: `px-2.5 py-[3px] gap-1.5` (`ConnectionChip.tsx:99`) vs the prototype's `padding:'3px 9px', gap:5` (Surfaces.jsx:1176-1177); and ours always paints the tone's flat `/10` background (`softBg`, `ConnectionChip.tsx:100`) whereas the prototype idles at 5% and only brightens to 10% on hover (`${m.color}0d` idle vs `${m.color}1a` hover, Surfaces.jsx:1179). Fix: `px-[9px] py-[3px] gap-[5px]`, and split idle (`/5`) vs hover (`/10`) background.

[Low] `DiagnosticsSection` Status-section values render `text-text-muted` (#a1a1aa, `DiagnosticsSection.tsx:106,109,114`) vs the prototype `kv()`'s brighter default value color `#d4d4d8` (Pages.jsx:838). Fix: `text-[#d4d4d8]` (static arbitrary value, safe under the Tailwind v4 JIT trap).
