## Findings (High → Low)

[High] AssistantBubble card chrome is entirely absent — assistant text renders as a bare markdown `<div>` with no background, border, radius, padding, or "Assistant" eyebrow, where the prototype gives it the same card treatment as the user bubble (mirrored corner). Prototype: `Messages.jsx:2064-2092` (`AssistantBubble`) — `padding:'11px 15px'`, `borderRadius:'4px 16px 16px 16px'`, `background:'rgba(255,255,255,0.04)'`, `border:'1px solid rgba(255,255,255,0.07)'`, plus the uppercase "Assistant" eyebrow. Ours: `TranscriptView.tsx:253-293` (`AssistantProse`) — the outer element is a plain `<div>`; `MarkdownErrorBoundary`'s wrapper only carries typographic classes (`font-sans font-light text-sm leading-relaxed …`), no `bg-*`/`border-*`/`rounded-*`/`px-*`/`py-*` at all. Note: `PARITY-LEDGER.md:333` disposes this row as "🔁 adapted" ("bare markdown div, no bubble shape/framing/eyebrow/copy chip") but — unlike its siblings at `:334`/`:335` (eyebrow, copy chip) — assigns no explicit owner to the missing *shape* itself, so the single largest visual gap in the whole transcript reads as resolved when it isn't (see Doc-drift notes). Fix: wrap `AssistantProse`'s content in a container matching `UserBubble`'s sibling shape mirrored — `rounded-[4px_16px_16px_16px] border border-white/[0.07] bg-white/[0.04] px-[15px] py-[11px]` (or the closest Tailwind arbitrary equivalents already used by `UserBubble` at `:979`).

[Med] User turns render as plain text — no markdown formatting at all — where the prototype runs user content through the same inline-markdown renderer (`Prose`) it uses for assistant text, so pasted bold/italic/inline-code/links still render specially on the user side. Prototype: `Messages.jsx:2094-2121` (`UserBubble` → `<Prose text={msg.content} isUser={true} …/>`, `renderProse`/`proseInline` at `:1732-1751`). Ours: `TranscriptView.tsx:976-984` (`UserBubble`) renders `{content}` as a raw string inside a `whitespace-pre-wrap` div — no `Markdown`/inline-formatting pass. Fix: route `UserBubble`'s content through a markdown pass (reuse `AssistantProse`'s `Markdown`/`MARKDOWN_COMPONENTS`, or a lighter inline-only variant) instead of a raw string.

[Med] Assistant prose text inherits the app's brightest text color instead of the prototype's dedicated, dimmer assistant-prose shade — losing the prototype's deliberate user-vs-assistant text-color contrast. Prototype: `Messages.jsx:2032` — `Prose` sets `color: isUser ? '#f4f4f5' : '#d4d4d8'` (assistant text is visibly dimmer than user text). Ours: `TranscriptView.tsx:267-273` (`AssistantProse`) sets no color class on its own wrapper, so it inherits `body`'s `--color-text-primary` (`#f4f4f5`, theme.css:48) — the SAME brightness as `UserBubble`'s `text-text-primary` (`:979`). Fix: add an explicit `text-[#d4d4d8]` (or a new `--color-text-prose` token) to `AssistantProse`'s wrapper div.

[Med] Diff view collapses the prototype's three-tier green/red vocabulary (soft pastel for line text/header counts, saturated for the sign glyph only, a third hue for the row wash) into one saturated tone applied everywhere. Prototype: `Messages.jsx:174-190` — header `+adds`/`−dels` counts use `#86efac`/`#fca5a5` (soft), row background wash uses `rgba(34,197,94,0.1)`/`rgba(239,68,68,0.1)` (green-500/red-500), and only the leading sign glyph (`:186`) uses the saturated `#4ade80`/`#f87171`. Ours: `TranscriptView.tsx:1268-1278` (`DIFF_ROW_CLASS`/`DIFF_SIGN_CLASS`) and the header counts at `:1295-1296` all use `tone-success`/`tone-danger` (`#4ade80`/`#f87171`) uniformly — row background wash is `bg-tone-success/10`/`bg-tone-danger/10` (a different base hue than the prototype's green-500/red-500), and line text + header counts render in the saturated shade the prototype reserves for the sign glyph only. Fix: give the row body text and header +/- counts a softer `text-[#86efac]`/`text-[#fca5a5]`, keep `tone-success`/`tone-danger` only on the sign glyph (`DIFF_SIGN_CLASS`).

[Med] Code block uses a bordered header BAR (divider row) with a muted-gray language label, where the prototype's `ProseCode` is headerless — the accent-pink `</>lang` label and copy button float directly over the code with no divider, saving vertical space. Prototype: `Messages.jsx:1813-1827` — no header row; label is `position:'absolute'`, `color:'var(--accent, #f472b6)'`, prefixed with a `</>` glyph; `pre` padding is `'38px 14px 14px'` to clear the floating label. Ours: `TranscriptView.tsx:360-378` (`CodeBlock`) — a real `<div className="flex items-center justify-between border-b border-shell-seam px-3 py-1">` header row, and the language label is `text-text-subtle` (muted gray, `#71717a`) with no `</>` prefix. Fix: drop the header/`border-b`, float the label (accent color + `</>` prefix) and copy button absolutely over the `pre`, matching the prototype's headerless layout.

[Med] The prototype's two darkest de-emphasis grays (`t4:#52525b`, `t5:#3f3f46` — `Messages.jsx:10`) have no corresponding token in `theme.css`, which bottoms out at `--color-text-subtle: #71717a` (theme.css:50) — a visibly brighter gray. Every row that should render at t4/t5 dimness instead renders at `text-subtle` (or `text-subtle/70`, still brighter than a true t5), so sub-labels and dim details read noticeably lighter than intended across the whole surface: `ToolCardShell`'s SUB micro-label (`TranscriptView.tsx:577-580` vs prototype `t5` at `Messages.jsx:114`), `RedactedThinkingBlock`'s label (`TranscriptView.tsx:1083-1085` vs prototype `#52525b` at `Messages.jsx:1457`), `SystemNoticeBox`'s trailing debug tag (`TranscriptView.tsx:1114-1116` vs prototype `#3f3f46` at `Messages.jsx:1441`), and `Seam` detail text (`TranscriptView.tsx:1244-1246` vs prototype `#52525b`/`#3f3f46` at multiple seam rows, e.g. `:1207`). Fix: add a `--color-text-faint` token (~`#52525b`) to `theme.css` and apply it at these sites instead of `text-subtle`/`text-subtle/70`.

[Med] `ToolInspector`'s family badge is hardcoded to accent-pink for every tool family, rather than the family's own identity color — inconsistent with both the prototype's per-family-colored inspector tag and with `TranscriptView`'s own `FAMILY_STYLE` map used one file over in the same feature. Prototype: `Messages.jsx:302` — the drawer's BASH tag is colored `FE_FAMC.bash` (lime-green), not a fixed hue. Ours: `ToolInspector.tsx:117-119` — `<span className="rounded bg-accent/10 px-1.5 py-0.5 … text-accent">{model.family}</span>`, regardless of `model.family`'s value. `TranscriptView.tsx:392-409` (`FAMILY_STYLE`) already has the correct per-family color map (bash lime, read blue, grep amber, etc.) that this component doesn't reuse. Fix: import `FAMILY_STYLE` (or a shared subset) and color the badge from `model.family`.

[Low] `RedactedThinkingBlock`'s lock icon is an emoji glyph (🔒) rather than a vector line-icon consistent with the rest of the icon system (every other icon in both codebases is an inline SVG stroke icon). Prototype: `Messages.jsx:1454-1456` (SVG `<rect>`/`<path>` lock). Ours: `TranscriptView.tsx:1080-1082` — `<span … aria-hidden>🔒</span>`. Fix: swap in an inline SVG lock matching the stroke-width/size convention used elsewhere (e.g. the `ApiErrorRow`/`RateLimitRow` icon style).

[Low] Prose line-height runs tighter than the prototype throughout: Tailwind's `leading-relaxed` (1.625) is used everywhere the prototype specifies 1.75–1.8. `AssistantProse`/`UserBubble` (`TranscriptView.tsx:270`, `:979`) use `leading-relaxed` vs prototype `Prose` `lineHeight:1.8` (`Messages.jsx:2032`); `ThinkingBlock`'s body (`TranscriptView.tsx:1068`) uses `leading-relaxed` vs prototype `lineHeight:1.75` (`Messages.jsx:1150`). Fix: use `leading-[1.8]`/`leading-[1.75]` arbitrary values at these sites (DiffView's `leading-[1.65]` already matches exactly and needs no change).

[Low] `AssistantProse`'s `font-light` (Tailwind weight 300) doesn't match the prototype's declared `fontWeight:200` for the message column. Prototype: `Chat.jsx:1282` sets `fontWeight:200` on the whole message-list container (our in-code comment at `TranscriptView.tsx:134-138` correctly notes this is deliberately scoped to `AssistantProse` only, not the whole column — that scoping choice is fine, see Deferred/intentional) but the weight value chosen, `font-light`, is Tailwind 300, not the 200 the prototype specifies. Fix: use `font-extralight` (200) instead of `font-light` (300) at `TranscriptView.tsx:270`.

[Low] `ToolCardShell`'s target text uses the app's global bright text color rather than the prototype's slightly dimmer Frame-E-specific target color. Prototype: `Messages.jsx:9` — `FE_T.t1:'#e4e4e7'`, used for the header target text (`:105`). Ours: `TranscriptView.tsx:557` — `text-text-primary` (`#f4f4f5`, theme.css:48), a brighter shade with no `#e4e4e7`-equivalent token available. Fix: add a `text-[#e4e4e7]` arbitrary value (or a token) for tool-card target text specifically.

[Low] Tool-card and thinking-block state dots render 1px larger than the prototype's. Prototype: `Messages.jsx:107` — `width:5, height:5`. Ours: `TranscriptView.tsx:562-565` (`ToolCardShell`'s state dot) — `h-1.5 w-1.5` (6px). Fix: `h-[5px] w-[5px]` (or accept as negligible; listed for completeness per the review's "state-dot" hint).

[Low] The prototype's own `FE_SD.failed`/`denied` dictionary specifies `#f08a8a` (`Messages.jsx:26,28`) for the tool-card failed/denied state word+dot, a slightly different (more washed-out) red than the `#f87171` used pervasively everywhere else in the same prototype file (`BASH_OUTCOME.error`, `ApiErrorRow`, `RateLimitRow`, `ResultRow`, `ToolResultRow`). Ours (`STATE_STYLE.error` → `tone-danger` `#f87171`, `TranscriptView.tsx:429-434`) matches the prototype's dominant `#f87171` convention, not the `FE_SD`-specific `#f08a8a` outlier. Flagged for completeness only — likely a prototype-internal inconsistency rather than intentional design; no fix recommended.
