## Bug 1 — `invalid_cwd: cwd is not an existing directory` sidebar rows

**Symptom.** Many sidebar rows are named after dead temp/fixture dirs
(`/private/tmp/catA`, `/private/tmp/cat-code-memory-save-before/fixture/...`);
opening one shows `invalid_cwd: cwd is not an existing directory: <path>`.

**Root cause — two layers.**
1. *Data hygiene (root):* the real `~/.cat-code/projects/` store is polluted with
   ~40 (of 60) transcripts whose recorded cwd is an ephemeral temp dir. Written
   by test/eval harnesses that ran the engine against the real config home
   instead of an isolated one (memory-behavior-eval `scripts/memory-behavior-eval/save-side.ts`;
   P3-8 credential tests `-private-var-folders-...-T-p3-8-cred-cwd-*`; scratchpad cwds).
2. *App surfacing:* the "openable" gate checks cwd *non-emptiness*, not
   *existence* — `app/renderer/src/sidebarState.ts:287`
   (`const openable = row.cwd.trim().length > 0`). A dead-but-non-empty cwd →
   `openable: true`, `intent: 'open-history'` → shown as clickable. It only fails
   at open time: `openHistorySession` (`app/renderer/src/App.tsx:1393`) →
   `resolveOpenHistorySession` returns `{spawn, cwd}` (`app/main/openHistorySession.ts:106`,
   passes the empty-cwd reject) → `host.createSession` re-validates on disk and
   fails at `app/host/host.ts:234`.

The host/resolver behavior is CORRECT (fail-closed, honest error). The defects
are the store pollution and the too-weak openable gate.

**Fix direction.** (a) One-off: clean the stale transcripts from `~/.cat-code/projects/`
(operator action — deleting real user state, needs sign-off). (b) Add a
cwd-existence signal so dead-workspace rows are filtered or marked "workspace
gone" up front like empty-cwd rows are. NOTE: the renderer has no fs access — the
existence check must originate sidecar/main-side (catalog entry gains an
`exists`/`openable` flag), which is a **protocol/wire addition** → this is why
Bug 1 is L and wants its own session. (c) Isolate the offending harnesses so they
stop writing to the real store.

## Bug 2 — tab shows workspace name instead of session name on open-from-history

**Symptom.** A sidebar row has a real name; opening it makes a tab whose label is
the workspace/cwd basename, not that name.

**Root cause.** Tab label falls back to cwd basename when `descriptor.title` is
null (`app/renderer/src/TabBar.tsx:396-401`). For a resumed/opened-from-history
session the title is never seeded — a two-sided gap in the P4-6 title-rider:
1. `resolveOpenHistorySession` reads the catalog entry (which HAS `title`) but
   returns only `{kind:'spawn', cwd, resumeEngineSessionId}` — drops
   `entry.title` (`app/main/openHistorySession.ts:106`); main then calls
   `host.createSession({cwd, resumeEngineSessionId})` with no title
   (`app/main/main.ts:1126`).
2. The sidecar title generator is fresh-only: built `resumed:true`
   (`app/sidecar/sidecarServer.ts:384`), `maybeGenerate` bails at
   `if (opts.resumed || !engineSessionId) return` (`app/sidecar/sessionTitleGen.ts:82`).
   The only two `broadcastSessionTitle` callers are the fresh-first-turn
   generator and the manual rename verb (`sidecarServer.ts:1088, 1608`). No path
   reads `getCurrentSessionTitle` on resume and re-emits it.

Sidebar shows the real name because it reads the catalog's `resolveEntryTitle`
(`app/sidecar/sessionsCatalogDomain.ts`); tab and sidebar disagree.

**Fix direction.** Carry `entry.title` through `resolveOpenHistorySession` and
pass it as `createSession({..., title})` — main-resolved from the catalog cache,
so HC1-safe (not renderer-authored). Alt: sidecar reads `getCurrentSessionTitle`
on resume and `broadcastSessionTitle`s it once.

## Bug 3 — active workspace jumps to top of the sidebar on open (parity regression)

**Symptom.** Opening a session yanks its workspace group to the top of the
sidebar. Should be frozen in place.

**Root cause.** `groupByWorkspace` sorts groups active-workspace-first —
`app/renderer/src/sessionsCatalogState.ts:379`
(`if (a.current !== b.current) return a.current ? -1 : 1`), where
`current = cwd === activeCwd` and `activeCwd` = the active session's cwd
(`app/renderer/src/Sidebar.tsx:182`). Opening a session recomputes `activeCwd` →
its group is forced to slot 0.

**This is a deviation from the prototype.** The prototype's
`groupByWorkspace(sessions)` takes NO `activeCwd` and sorts purely alphabetically
(`'other'` last) — `~/catcode_prototype/cat-app/Sidebar.jsx:26-38`. Its comment
says "current workspace first" but the code never implements it; the migration
implemented the misleading comment literally (repo mistake #2 — trusting a doc
over source, here a stale prototype comment). The operator's expectation (freeze)
matches the ACTUAL prototype.

**Fix direction.** Drop the active-first tiebreak so groups stay alphabetical.
Caution: `groupByWorkspace` is shared with the Sessions page, which still uses
`group.current` for a highlight (`app/renderer/src/SessionsPage.tsx:238`) — keep
computing `current` for styling, just stop SORTING by it. Sidebar render doesn't
use `group.current`, so nothing is lost there.

## Bug 4 — task/agent-completion notification renders as a user (right-side) bubble

> **SUPERSEDED 2026-07-26.** The mechanism below ("`origin` … does NOT cross the
> app wire") was true when written and is no longer. `SDKUserMessage.origin` now
> crosses (app/shared/protocol.ts `EventFrame` §User-turn provenance), the
> text-sniff fix recorded here has been replaced by an authoritative read of that
> field, and the same fix covers the four other injected kinds this sweep did not
> reach (`coordinator`/`channel`/`teammate`/`deferred-continuation`). Kept as the
> historical record of the 2026-07-21 diagnosis; do not act on its wire claim.

**Symptom.** A "Task notification / Task ID / … / Result: …" banner (a background
agent completion, e.g. "Agent @Hamilton completed") appears as a right-aligned
pink USER bubble, as if the operator typed it. Seen on a resumed
`~/catcode_prototype` session, but NOT terminal-specific (see below).

**Root cause.** The engine injects task notifications as **user-role** turns:
`enqueuePendingNotification` with `mode:'task-notification'` +
`origin:{kind:'task-notification'}` (`src/utils/messageQueueManager.ts:143-154`,
minted at `src/tasks/LocalMainSessionTask.ts:253-255`,
`formatTaskNotificationText` in `src/utils/taskNotification.ts:29`). The
`origin` marker the TUI uses to render it distinctly is an internal engine
`Message.origin` field — it does NOT cross the app wire and the projector never
reads it. So the desktop sees only a `user` frame whose text is
`"Task notification\n..."`, and `projectUserContentBlock`
(`app/renderer/src/transcriptProjector.ts:1456-1476`) special-cases only
`<command-message>` echoes; everything else becomes
`{kind:'user-text', role:'user'}`, rendered right-aligned
(`app/renderer/src/TranscriptView.tsx:247`, `1132-1138` `flex justify-end`).

**Not terminal-specific.** The projector runs identically for live and resumed
sessions; any transcript containing a task notification mis-renders. The operator
saw it here because that prototype session ran orchestrator/agent (Task) work
that injected these. (Whether the desktop can itself spawn background-agent tasks
that inject notifications is a separate question; the RENDER bug is
origin-agnostic.) Likely a broader class: other engine-injected user-role texts
that aren't `<command-message>` would also mis-render.

**Fix direction.** Detect task-notification text in the projector using the
engine's existing `isTaskNotificationText` / `parseTaskNotificationDetails`
(`src/utils/taskNotification.ts:105,114`) and emit a distinct NOTICE row kind
(not `user-text`). Needs: new row type in the projector union + `TranscriptView`
case + `sdkMessageFixtures.ts` + both exhaustiveness tripwires (repo §7). M-sized
because it adds a transcript row kind. Consider generalizing to other
engine-injected user-role banners.
